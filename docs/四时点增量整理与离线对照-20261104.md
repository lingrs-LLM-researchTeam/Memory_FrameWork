# Framework 1.2.0 四时点增量整理与离线对照

2026-11-04。四时点模式在两组各 264 条消息的离线回放中均覆盖 100% 的输入。相较按轮数触发，摘要的预计总 token 分别减少 4.48% 和 8.38%。消息越集中在同一会话和同一窗口，固定提示词的重复次数越容易下降。

## 启用与运行

安装 `dist/astrbot_plugin_livingmemory-memoryfw-1.2.0.zip`。在 AstrBot 插件配置「记忆生成设置 → 自动整理触发方式」选择 `daily_slots`，保存后重载。选择 `rounds` 恢复原有轮数触发，旧配置默认使用该模式。对应配置片段如下。

```json
{
  "reflection_engine": {
    "summary_trigger_mode": "daily_slots",
    "summary_trigger_rounds": 10
  }
}
```

- 四个时点使用北京时间（UTC+08:00），定时唤醒复用已有后台恢复任务的 15 秒检查周期。00:00 收尾前一自然日。四段区间依次为 [00:00, 08:00)、[08:00, 13:00)、[13:00, 18:30)、[18:30, 次日 00:00)。恰好在边界的新消息归入后一段。
- 消息即时采集。每个非空会话从已有成功游标开始，继续遵守权限、来源、人格、作用域、跨日和长时间空闲的切分。每次最多读 200 条，超出后继续分批。实际模型调用数取决于非空会话和分段数。
- 任务保存精确来源窗口，写入成功后提交游标。从异常退出恢复时，按已过时点和游标补跑。未成功的窗口保留在队列，通常在下一时点重试，达到既有的三次任务尝试上限后按原机制处理。已撤销来源须重新校验。迟到消息保留原始发送时间，并排在已采集消息之后等待整理。
- 切换模式沿用原游标。切换前已有待重试任务会优先恢复。旧任务若含当前截止时点之后的消息，待整个任务符合截止条件再执行。停机跨过多个时点后，在恢复时段内按消息所属窗口补齐。正常运行时新消息等待下次整理的最长间隔为 8 小时，另加排队与模型耗时。
- 该设置控制自动对话摘要。手动总结、聊天时的召回注入、独立学习调度以及其他模型调用有各自的触发条件。升级前保留同一时刻的配置和数据库备份；若需回退旧版，应同时恢复匹配的备份，特别是已有迟到消息的会话。

## 相同消息与实际执行路径

每种负载用相同输入分别在两套空数据库上回放，两模式各自的输入 SHA-256 一致。全日组按窗口均匀投放合成群消息，每个窗口分别给三个会话 50、15、1 条。晚间组只读复用 10 月 22 日 20:37–23:39 的消息时序、角色和匿名会话分组，以合成文本替换全部正文。两组都使用合成群场景及测试人格。回放时每次写入后及经过边界时检查队列，并在次日 00:00 取数。轮数模式按默认 10 轮运行，未人为强制清理尾批。

测试使用打包安装的 Framework、实际 SQLite 任务表、整理器、提示词、记忆存储及本地向量实现。摘要 Provider 和 Embedding 使用本地替身，外网连接在测试运行器内被阻止。每次进入替身 Provider 的 `text_chat` 计一次调用。覆盖分母为全部输入消息，分子为成功提交且可在存储中找到来源链接的唯一消息，和完成作业、游标交叉核对。覆盖率衡量处理范围，语义质量需要另行评价。

| 消息分布 | 模式 | 摘要调用 | 午夜已覆盖 | 预计输入 | 预计输出 | 预计合计 |
|---|---|---:|---:|---:|---:|---:|
| 全日分散，3 个会话 | 轮数 | 13 | 260/264（98.48%） | 47,235 | 825 | 48,060 |
| 全日分散，3 个会话 | 四时点 | 12 | 264/264（100%） | 45,080 | 828 | 45,908 |
| 晚间集中，7 个会话 | 轮数 | 10 | 200/264（75.76%） | 36,474 | 620 | 37,094 |
| 晚间集中，7 个会话 | 四时点 | 7 | 264/264（100%） | 33,329 | 657 | 33,986 |

全日组中，两种模式都完整覆盖了活跃和中等流量会话的同一批 260 条消息。只比较这 260 条，调用从 13 次降到 8 次，预计总量从 48,060 降到 35,940（−25.22%）。其中 200 条活跃会话从 10 次降到 4 次，60 条中等会话从 3 次增到 4 次。剩余 4 条分散在四个窗口的安静会话在四时点模式中触发 4 次摘要，共增加预计 9,968 token。轮数模式在观察截止时仍保留这些消息等待后续触发。

晚间组的 264 条消息都在最后一个窗口，各会话各生成一次摘要。四时点模式多覆盖了 64 条原本顺延的消息，同时少发 3 次请求。这个样本仅代表一个晚间的流量分布。

## Token 估算与复现

输入取实际发往替身 Provider 的 system 和 user 两段提示词，使用便携包已有的 Qwen 文本词表做 NFC 归一化和字节对分词。输出替身按每批出现的合成工单生成去重事实和 JSON，再用相同词表计数，输出可以随批量增长。词表 SHA-256 为 `b2b1b8dfb5cc5f024bafc373121c6aba3f66f9a5a0269e243470a1de16a33186`。表内为摘要文本的估算量。真实服务的分词、聊天封装、输出长度、隐藏推理、缓存命中和计费可能不同；本次没有在线 usage。该实验未测量聊天生成、注入、Embedding 或学习模块的用量。

在框架根目录准备本地 AstrBot 核心、测试依赖和词表，并使用一个尚不存在的隔离输出目录。需要复现晚间组时提供该日的原始数据库或一致性只读副本；省略该参数可独立复现全日组。

```sh
python -B tools/build_release.py
python -B tools/run_regressions.py --core "<本地 AstrBot 核心目录>" --test-deps "<离线测试依赖目录>" --output "<新输出目录>" --comparison-vocab "<本地 qwen.tiktoken>" --comparison-timeline "<conversations.db>"
```

分会话数值、输入指纹、版本和回归计数见 [1.2.0 验证结果](validation-1.2.0.json)。调度入口见 [summary_recovery.py](../plugins/astrbot_plugin_livingmemory/core/summary_recovery.py)，四个边界见 [summary_schedule.py](../plugins/astrbot_plugin_livingmemory/core/summary_schedule.py)，回放程序见 [test_summary_mode_comparison.py](../plugins/astrbot_plugin_livingmemory/tests/test_summary_mode_comparison.py)。
